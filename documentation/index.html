1.2 What the service is, in one paragraph#

Seleric Agent answers business questions in natural language. A user's message is stored as a run; a worker executes one tool-calling language-model loop that fetches governed numbers from Seleric Agent Core (an MCP gateway over Cube), may call analysis helpers (diagnosis, breakdown, forecast, exploration, Python over fetched results), and writes an answer. Every figure in the answer is then checked in code against what the tools returned; one corrective pass runs if a figure fails; the answer ships with KPI cards, a table or a chart chosen from the shape of the data. The service also keeps conversations, memory and attachments, drafts and sends approved emails, serves the Office web UI, takes voice sessions, and runs scheduled health snapshots and target monitoring.

2.4 What the service does not do#

  • It does not hold business data or definitions; metrics and dimensions come from the Core catalogue at run time.
  • It does not write to ads platforms or other business systems; its only outbound write is approved email.
  • It does not query ClickHouse or Cube directly.

3. High-level design#

3.1 Purpose and scope#

Purpose. Let a business user ask a question in plain language and receive a short, correct, evidence-backed answer with the right visual, without the model ever producing a number that the data did not.

In scope

  1. A conversation API: threads, messages, runs, memories, attachments, feedback, search, events (server-sent).
  2. Durable, leased execution of runs by a separate worker, with retries, cancellation and recovery.
  3. One reasoning loop (PydanticAI) over the Core MCP tools and local analysis tools.
  4. Deterministic verification of the figures in each answer, and deterministic selection of the visual.
  5. Analytical engines: diagnosis, exploration, composition, forecasting, entity audit, sandboxed Python.
  6. Approval-bound email.
  7. Business-health snapshots and target monitoring with an Ops/Monitoring API and UI.
  8. The Office web UI and a voice channel.

Out of scope: the data platform, the metric catalogue and the Cube model (Mage AI platform and Agent Core), dashboards, any write to business systems other than email.

3.5 Principal design decisions#

# Decision Reason (from the code)
D1 One reasoning loop, not a graph of specialist agents Ported from the earlier test agent's shape: user → model ⇄ tools → answer; fewer hand-offs, lower latency
D2 The model never fetches evidence ids across calls for heavy analyses; diagnosis and exploration are single composite tools that fetch and compute Passing hundreds of ids through the model corrupted them
D3 Figure verification is deterministic code, not a critic model Reproducible and free of model latency
D4 Visuals are chosen from the shape of the result by code No model call, no added latency, labels and units agree with the table builder
D5 Metrics, dimensions and views are never named in code They come from the live catalogue snapshot; scripts/lint_semantic_literals.py enforces this
D6 The API enqueues, a separate worker executes Runs survive API restarts; concurrency and drain are controlled in one place
D7 Attempts are leased and fenced by a version A late worker cannot overwrite the result of the attempt that replaced it
D8 Per-model health cooldown in the fallback chain FallbackModel restarts at the first model on every request; without cooldown a rate-limited model made a ~10 s answer take 60–120 s
D9 Email approval is bound to the exact content Any edit voids the approval; a draft is handed to the transport at most once

3.7 Known limitations (verified)#

  1. API rate limiting exists in code (RATE_LIMIT_ENABLED, per-minute limit) but is off in the deployment.
  2. The POST /v1/threads/{id}/messages route rejects any execution_mode other than development; POST /v1/missions accepts only read_only mode and development execution mode.
  3. Memory vector retrieval is unavailable without pgvector; the migration continues with lexical retrieval by design.
  4. config/diagnostic_policies.yaml and config/experiment_registry.yaml are not read by any Python file in src/.

4.4 Answer assembly#

  1. The loop returns text. Metric ids that slipped into prose are replaced by catalogue labels; long decimals are rounded; Indian digit grouping is applied (answer_text.py).
  2. grounding() yields per-figure findings; problems() turns them into sentences; at most one correction run follows; lost_substance() keeps the original if the rewrite drops verified content; remaining issues append unverified_note and set the limitation UNVERIFIED_FIGURES.
  3. If evidence exists and no limitation applies, present.attach() adds parts: KPI_GRID, TABLE, CHART according to result shape.
  4. The runner writes the assistant message with typed parts (TEXT, TABLE, CHART, KPI_GRID, SOURCE, WARNING, APPROVAL, AGENT_STATUS, ...), a mission result, V3 artifacts, and activity events; the placeholder message created at submission is replaced.
  5. LoopResult.status is failed when the answer is empty, partial when a limitation exists (ANSWER_TRUNCATED, DEGENERATE_OUTPUT, EXECUTION_LIMIT_EXCEEDED, UNVERIFIED_FIGURES), otherwise completed.

4.6 Memory flow#

On every submitted user message, MemoryCandidateExtractor.extract(message, thread) produces candidates and MemoryService.ingest_candidates stores them. The memories.status column defaults to PENDING_CONSENT, and a database constraint allows ACTIVE only when consented_at is set; the other statuses are CANDIDATE, SUPERSEDED, ARCHIVED, DELETED. Users manage them through /v1/memories* (pin, confirm, move scope, archive, delete). ContextBuilder selects memories for a run and records the selection (run_memory_usage). Scopes are THREAD, USER, PROJECT, EPISODIC; episodic events are stored in episodic_events. Retrieval is lexical (generated search_vector column, ts_rank with websearch_to_tsquery); the optional embedding vector(1536) column exists only when pgvector is installed, which it is not.

4.9 Scheduled data flows#

Domain-health snapshots (business-state-cron)#

services.domain_health.scheduler resolves, per domain, the metrics listed in config/domain_health_profiles.yaml through the semantic port (MCP), applies business_state_profiles.yaml features and the judge (judge.py), and writes JSON snapshots under SELERIC_DOMAIN_HEALTH_DIR (volume domain_health). The loop calls the scheduler every 60 seconds; the scheduler decides what is due. The agent reads the latest snapshot through business_snapshot; GET /v1/monitoring/state and POST /v1/business-state serve it.

Target monitoring (monitoring-cron)#

services.monitoring.runner --brand 20 reads monitor.metrics, monitor.targets_current, monitor.known_periods, fetches series through the semantic layer, evaluates each metric against its floor/target/ceiling (evaluate.py), and writes monitor.evaluations, monitor.findings and monitor.finding_events. It never touches ClickHouse.

Forecast scoring#

python -m seleric_swarm.forecasting.score --if-due (once a day, driven by the business-state loop) compares stored forecast artifacts (v3_artifacts) with days that have since matured and writes reports into the forecast_reports volume (SELERIC_REPORTS_DIR).

5.2 Submission#

  1. POST /v1/threads/{thread_id}/messages (HTTP 202).
  2. Checks in order: thread owned by the caller and ACTIVE (409 otherwise); execution_mode is development (400); optional parent_message_id belongs to the thread (422); at least one non-empty TEXT part (400); each attachment belongs to the thread, is READY and CLEAN, and is not yet linked (409/422); the requested date axis in scope is valid (422).
  3. The context bundle (history, memories, summary) is built and a mission row is seeded as running (503 if it cannot be persisted).
  4. One database transaction creates the run (max_attempts from settings), attempt 1 as RETRYABLE, the user message, an assistant placeholder message with an AGENT_STATUS part "Working…", the attachment links, the run metadata (context_bundle, submission with query, time zone, as_of, date axis, request id, execution mode, placeholder id), memory usage records, the thread title (first 80 characters of the query when the title is empty or "Untitled conversation"), and a submission_outbox row.
  5. Memory candidates are extracted, the run.queued event is emitted, and the run is dispatched: the durable queue sends a Postgres NOTIFY so a listening worker starts immediately; polling remains the fallback.

5.3 Claim, lease, heartbeat, retry#

sequenceDiagram
  participant W as Recovery worker
  participant DB as Postgres
  participant X as Executor (runner)
  loop every --interval seconds, or on NOTIFY
    W->>DB: SELECT runnable attempt FOR UPDATE SKIP LOCKED (RETRYABLE, or lease expired) - set worker_id, lease_expires_at = now + RUN_LEASE_S, version + 1
    W->>X: execute run in a free slot (up to run_max_concurrency)
    loop every RUN_HEARTBEAT_S
      W->>DB: heartbeat: extend lease only if lease_expires_at > now and version matches
    end
    alt success
      X->>DB: mark attempt and run COMPLETED, emit terminal event
    else retryable error
      W->>DB: transition_failed_attempt: next attempt RETRYABLE after delay
    end
  end
  Note over W,DB: recover_expired() turns RUNNING attempts with an expired lease into retryable or failed
  • Retry delay: RUN_RETRY_DELAY_S × 2^(attempt-1) plus uniform jitter up to RUN_RETRY_JITTER_S.
  • A cancelled run's expired attempt is moved to CANCELLED instead of being retried.
  • Concurrency: run_max_concurrency (4) missions per worker. Before 2026-10-07 each poll waited for its whole batch; dispatch now claims as many runnable attempts as there are free slots without waiting for running ones.
  • Shutdown: on SIGTERM the worker stops claiming and lets running missions finish for up to run_drain_timeout_s (480 s); the container's stop_grace_period is 9 minutes by default.
  • The terminal event is emitted only after the compare-and-set of the terminal state succeeds; every state change is fenced by the attempt version.

5.4 Cancellation#

  1. POST /v1/runs/{run_id}/cancel records the cancellation (runs.cancel with a terminal run.cancelled event; 409 if the run is not cancellable) and replaces a pending "Working…" placeholder with "Run cancelled.".
  2. The cancellation flag for the run's mission id is set (cancellation.request(run.mission_id); Redis when CANCELLATION_BACKEND=redis, deployed).
  3. The loop checks the flag before every model request (PrepareTools.prepare raises MissionCancelledError) and local tools accept an is_cancelled callable.
  4. The legacy mission route POST /v1/missions/{id}/cancel marks a running mission cancelled (best effort).

5.5 Streaming progress to clients#

GET /v1/runs/{id}/events returns stored activity events; GET /v1/runs/{id}/events/stream (and /v1/threads/{id}/events/stream) serve the same as server-sent events. 5.7 Email approval#

  1. The model calls draft_mom_email or draft_ad_hoc_email; recipients are an explicit well-formed address or a name in config/email_contacts.yaml (otherwise the agent asks); EMAIL_ALLOWED_DOMAINS (default seleric.ai) restricts free addresses.
  2. A preview record is stored in the shared record store; the UI renders an APPROVAL card.
  3. The user approves through the card (POST /v1/emails/{id}/approve) or by spoken or typed approval via send_email. send_email refuses a version the user has not seen (produced by the same run), a stale version, another user's draft, and a cancelled run.
  4. send marks the record SENDING before awaiting the transport; retries return the current record; a definite refusal (FAILED) may be retried with the same approval; an unknown outcome (timeout) is never retried automatically; SUBMITTED means the provider accepted the message, not that it was delivered.

5.8 Voice session#

  1. The browser calls POST /v1/voice/token; the API mints a LiveKit JWT scoped to one room derived from a thread the caller owns, with the principal as participant metadata.
  2. The seleric-voice worker joins the room. Its conversational voice model is instructed (in voice/worker.py) to answer small talk itself and to call the tool ask_seleric with the user's complete question for anything analytical, then speak the result; email requests also go through ask_seleric, and spoken confirmation words ("send", "yes", "go ahead") trigger approval of an already shown draft.
  3. voice/projection.py gives the voice model a short projection (last turns, durable preferences), never tool payloads or evidence.
  4. SpeechQueue plays one utterance at a time: answers keep their order, status chatter is dropped when something is speaking, and the user can talk over speech, which drops the rest and everything queued.
  5. The worker is a client of the same conversation API (SELERIC_API_URL), including POST /v1/runs/{id}/cancel.

The module docstring of voice/worker.py still describes "Phase 0: echo only"; the code and prompts it contains implement the conversational agent.

6.4 The MCP gateway and tool wrapper#

Gateway (protocols/mcp/gateway.py)#

MCPGateway reads config/mcp_servers.yaml (one server, seleric, streamable_http, URL from SELERIC_MCP_URL, bearer from SELERIC_MCP_TOKEN, capability prefix seleric) and exposes call(tool, args) and tool listing (protocols/mcp/servers/seleric_remote.py). /readyz lists the discovered capabilities.

Tool wrapper (agent/mcp_toolset.py)#

The loop is allowed only these 17 Core tools (ALLOW): catalogue_search_metrics, catalogue_get_metrics, catalogue_get_metric, catalogue_list_dimensions, catalogue_resolve_dimension, catalogue_resolve_term, catalogue_resolve_concept, catalogue_resolve_values, catalogue_resolve_brand, catalogue_list_brands, catalogue_get_ontology, catalogue_related_metrics, modules_list, metrics_query, metrics_drilldown, insights_explain, build_dataset_query. It does not get semantic_sql or any actions_* / ads tool. tool_defs() sorts and cleans the schemas so the prompt prefix stays byte-stable.

Per call:

  1. validate() against the published JSON Schema (Draft 2020-12) and filter_misuse() for known misuse (for example set/notSet filters carry no values: VALUELESS_OPS).
  2. De-duplication inside the turn: TurnState.seen maps a call signature to a future, so an identical call is served from the turn's cache (duplicates counter).
  3. Execution through the gateway with TOOL_TIMEOUT_S (45 s default, AGENT_TOOL_TIMEOUT_S); QUERY_ROW_LIMIT (100,000) is applied to query tools (with_full_limit).
  4. Post-processing: flag_partial marks windows that include the still-open day; flag_row_limit; flag_composed for multi-part results; compact() drops plumbing keys (DROP_KEYS: Cube query, SQL, catalogue sha, serve objects, ...), caps lists at MAX_ROWS (60) and the result at MAX_RESULT_CHARS (14,000) while keeping rows and compare_rows even when empty.
  5. write_evidence stores up to MAX_EVIDENCE_ROWS (5,000) evidence points per result; going over is flagged on the payload, never silent. build_dataset_query results are paged (DATASET_PAGE 5,000) up to MAX_DATASET_EVIDENCE.
  6. Failures are returned to the model as tool results, never raised.

TurnState collects payloads, evidence, evidence_ids, by_query (query id → evidence ids), steps, parts (structured answer parts), tables (offered tables), prior_queries, errors, seen, counters tool_calls, duplicates, tool_ms, and today.

6.7 Grounding (agent/grounding.py)#

Input: the answer text and the list of tool payloads of the turn (plus earlier turns' compact payloads and the figures quoted in the conversation).

  1. answer_numbers(text): character scan (no patterns) returning each stated number with value, pct, tol. tol is one unit of the last digit shown, scaled by suffixes (k, m, l/lakh, cr/crore), and never below 0.01. Dates, times, years and bare integers under 32 are skipped.
  2. Pools: all numbers in all payloads (payload_numbers), split by sign; per-entity pools from labelled rows (payload_rows: row labels such as campaign or day names mapped to the numbers of that row); numbers outside any labelled row ("loose": totals, deltas, percentages); and, for tiny payloads (SMALL_POOL), per-payload pools.
  3. Entity scoping: for each answer line, entities named on the line (or on a preceding header line with no numbers, until a blank line) bind that line's numbers to those entities' rows.
  4. Classification per number: measured when found in the pool within tol × 1.01 (also as a percentage ÷ 100); derived when one arithmetic step (sum, difference, ratio, % change, share) of two numbers that can meaningfully combine reproduces it — arithmetic is restricted to a row's own entity plus totals, because across hundreds of numbers almost any figure is a sum or ratio of some pair; misbound when the value exists in the data but belongs to another entity than the one its line is about; sign mismatch when only the opposite sign exists; unmatched otherwise. placeholders() finds a ? standing in for a value.
  5. problems(g) renders one sentence per finding; correction_message(issues) is the text of the corrective run; unverified_note(issues) is appended when issues remain; lost_substance(before, after) rejects a rewrite that kept under 60 % of the verified figures when the draft had at most a quarter of its figures flagged.

6.9 Model chain (agent/model.py, agent/model_health.py, llm/)#

6.10 Persistence layer#

  • persistence/migrate.py applies SQL files in order; postgres.py, file_store.py, memory.py implement the mission store; v3_artifacts.py stores typed artifacts.
  • conversations/repositories.py defines the repository interfaces; conversations/postgres.py implements them with SQLAlchemy and raw SQL. Writes that must be atomic use repositories.transaction() (used by message submission).
  • Run claiming (conversations/postgres.py): claim(run_id, worker_id, lease_seconds) selects a runnable attempt FOR UPDATE SKIP LOCKED where the worker is null or the lease expired, sets worker_id, lease_expires_at, increments version; heartbeat extends the lease only while lease_expires_at > now and the version matches; transition_failed_attempt(..., retry_delay_seconds) moves to the next attempt or to failed; list_recoverable feeds recover_expired.
  • Outbox: submission_outbox rows are written in the submission transaction (add_outbox); the queue marks them as delivered.
  • Events: conversations/events.py appends ActivityEvent rows and notifies readers; event_mapping_v1.py maps mission events to conversation events.
  • Blobs: conversations/blobs.py provides MinioBlobStore, local store, and ClamAVMalwareScanner / UnavailableMalwareScanner.
  • Privacy: conversations/privacy.py holds visibility primitives. Payloads are delivered as stored (no value redaction); access is enforced by principal and workspace checks and a capability-limited public-field allowlist.

6.11 Recovery worker (recovery.py)#

DurablePollingRunQueue is the durable queue (the QUEUED run / RETRYABLE attempt rows are the queue); enqueue also sends NOTIFY on RUN_CHANNEL, and listen_for_runs listens in a background thread and wakes the poll loop; InProcessRunQueue is the development equivalent. RunRecoveryWorker.run_forever polls, dispatches into free slots (_dispatch), and heartbeats each running attempt (_heartbeat, RUN_HEARTBEAT_S). RunRecoveryService.fail_attempt and recover_expired implement retry and lease recovery with delay RUN_RETRY_DELAY_S × 2^(attempt−1) plus jitter. The executor given on the command line (api.conversations:build_submission_executor) rehydrates query, scope, request id, execution mode and placeholder id from Run.metadata.submission and calls agent.runner.run_v3_mission.

All engines are pure calculation over series that a toolset has already fetched through the certified Core path. Nothing in the engines names a metric, dimension, value or business threshold; the catalogue supplies lineage and structure.

7.1 Diagnosis: "why did it change?" (toolsets/diagnosis.py, causal/diagnosis.py, causal/dowhy_service.py)#

Division of labour. The toolset diagnose_metric_change plans candidates from catalogue metadata (the outcome's formula.depends_on, ratios built on it, segments by dimension), fetches about two months of daily history per candidate through the same path as metrics_query, writes evidence, and passes the series to the engine. Fetching and calculation are one tool call because handing hundreds of evidence ids through the model corrupted them.

The engine reports four layers separately so an arithmetic decomposition is never presented as a behavioural cause:

Layer Question Method
1. Event Is the change real? The event is compared with the same weekday in recent weeks (outlier weeks skipped), judged against a robust day-of-week plus trend fit (fit_calendar, Huber). Referencer builds level-adjusted same-weekday references; SeasonalProfile measures normal deviation on a log scale with median/MAD over windows that touch no abnormal day. A change inside normal variation is reported as such
2. Decomposition (what changed) Which accounting parts moved? Candidates from catalogue lineage in both directions, accepted only when the data verify them day by day (Y = k × Π X_i^e_i with constant k); additive bridges found by discover_bridge_tree (signed sums of up to six terms, meet-in-the-middle over random projections, each accepted only if it reproduces the metric on every history day); the change is split with exact, order-independent Shapley values (shapley); approximate rate chains (metric ≈ k × rate × base) are reported as approximate
3. Localisation (where) Which segments? Segment decomposition over catalogue dimensions: additive metrics split exactly; a rate splits into a mix effect and a within-segment rate effect (where Simpson's paradox shows); a ratio of two sums splits exactly; each dimension's segment-specificity is compared with the specificity a normal day shows, and identifier-like dimensions are ignored
4. Drivers (why) Which upstream candidates, with what evidence? DoWhy on an explicit time-series DAG (estimate_time_series_effect): calendar and lagged pre-treatment variables only, HAC intervals, refuters plus temporal-precedence tests. Contribution = effect × how far the driver itself moved from its reference

Driver classification is rule-based and conservative: supported_cause (identified effect, confidence interval excludes 0, every refuter passes, the driver moved at the event in the explaining direction, and past driver values predict the outcome while the reverse does not); likely_contributor (same, but direction rests on an assumption); correlation (adjusted effect indistinguishable from 0, a placebo refuter fails, or the outcome feeds back into the driver); insufficient_evidence. A driver in lockstep with the outcome's own unit count is treated as a measurement of the same events, not a cause (unit_count_metric, _lockstep_correlation). DoWhyService requires a registered causal question; any failure raises DoWhyUnavailable so the caller falls back to a metadata-only audit.

Output: DiagnosisReport with a headline, exact bridge lines reconciled to the total, narrative sentences in the outcome's own units, and the driver findings.

7.2 Exploration: "what is worth knowing?" (toolsets/exploration.py, exploration/)#

space.py plans the subspace (metrics × dimensions) from catalogue metadata; engine.py runs a batch of hypothesis tests:

Test Scope
period_change each metric's window against the previous window, judged against window-to-window moves in its own history
trend, change_point each metric's fetched daily history
distribution_shift each additive metric × dimension: Adtributor explanatory power plus surprise over the window change
outstanding one segment far larger than the rest predict
co_movement day-to-day changes across metrics, skipped for pairs the catalogue already relates (lineage or the same units measured twice)

Every test yields a p-value under its own null; Benjamini–Hochberg across all tests (not only the reported ones) holds the false-discovery rate at EXPLORE_FDR (0.10, a constant in toolsets/policy_config.py); survivors must clear a practical-size floor and are ranked by kind prior × impact × significance. Each insight carries typed follow_ups (a registered tool and arguments) so a later turn can drill into the segment or diagnose the move. All insights are observations except co-movement, which is an association; none is a cause. _dedupe keeps one insight per movement.

7.3 Composition (toolsets/composition.py)#

break_down_metric walks a metric's catalogue formula.composition tree (for example net profit = contribution margin − ad spend), fetches every line in one query per period on the metric's own view and basis, and checks the reconciliation itself, so breakdowns, waterfalls and period bridges never mix bases.

7.4 Forecasting (toolsets/forecasting.py, forecasting/, chronos/)#

flowchart LR
  P[forecast_metrics: metric ids, horizon] --> PL[compile_forecast_plan]
  PL --> G1[gates: eligibility and temporal gates with reason codes]
  G1 --> FR[feature frame: history, calendar, known-future and past covariates, masked data incidents]

  • Quality machinery: backtest.py (offline rolling-origin backtest and bundle promotion, writes reports/forecasting/<date>/<target>.json|.md and proposes a YAML bundle for human approval), bakeoff.py (feature-set bake-off: calendar vs none, then each candidate past covariate, then a second covariate; a feature stays only if it lowers held-out error), calibration.py, gates.py, score.py (scores stored forecasts against matured days; run daily by the cron).
  • Only the ForecastArtifact supplies numbers to the answer.

7.5 Domain health and business state (services/domain_health, services/business_state)#

business_state computes per-metric features (period delta, rolling means, anomaly detectors in detectors.py) over daily series according to config/business_state_profiles.yaml. domain_health resolves the metrics of each domain (config/domain_health_profiles.yaml, overridable by users through the monitoring API) into snapshots and judges the latest value (judge.py): change is reported in the unit that fits the metric's shape (percent for additive metrics, percentage points for ratios, absolute for signed ones); severity requires the move to go the metric's bad way, and a metric without direction_bad can only be watched, never alerted; the band accounts for weekday seasonality and does not go below zero for metrics that cannot be negative.

7.6 Target monitoring (services/monitoring)#

12.3 Gaps that follow from the design#

  1. One shared key means one identity. With a single API_KEY and TRUST_IDENTITY_HEADERS off, every caller is workspace default, user default; ownership checks then separate nothing between callers. Per-user separation requires a trusted proxy that sets identity headers (and TRUST_IDENTITY_HEADERS=true) or an external authenticator.
  2. /docs and /openapi.json are unauthenticated and list every route.
  3. Rate limiting is disabled in the deployment.
  4. The default Postgres credentials in docker-compose.yml are seleric/seleric; the override binds Postgres to loopback to keep them off the network (comment in the override file).
  5. Jenkinsfile.eval is the only pipeline for this repository and runs static gates only; there is no automated deployment or secret scanning stage in it.
  6. The voice worker module docstring is stale (describes an echo-only phase), which can mislead a reviewer about what the worker does.

13.6 Backup and data lifetime#

State lives in Postgres (volume seleric_postgres), MinIO (seleric_minio), the domain_health and forecast_reports volumes, and the files under .data/ (sandbox work directories per mission). The repository defines no backup job for these volumes. Conversation data has no automatic expiry in the code; deletion happens through the API (DELETE /v1/threads/{id}, DELETE /v1/memories/{id}, DELETE /v1/attachments/{id}).

14.3 Rules to keep#

  • No metric, dimension, view or brand literals in code. scripts/lint_semantic_literals.py enforces this with semantic_literal_allowlist.txt; everything semantic comes from the live catalogue snapshot.
  • Numbers come from tools. A model-computed figure must go through run_python so it is grounded.
  • Tool failures are results, not exceptions, inside the loop.
  • Best-effort telemetry never fails a mission.
  • Durable first. Long-running work should be a run attempt claimed by the worker, with cancellation checked cooperatively.
  • Email stays approval-bound. Do not add a path that sends without the content-hashed approval.
  • No new language-interpreting patterns: the grounding scanner is a character scan on purpose.
  • Python 3.11+ (images use 3.12), line length 100.

14.4 Evaluation practice#

eval/regress/run_regression.py <questions.json> <out_dir> <repeat> replays questions against the deployed API and checks the numbers against ClickHouse. When changing one behaviour, run the relevant questions rather than the full set. eval/regress/ab, agent6_checks.py, mcp_direct.py and ch.sh support it.

Bundle (context) History, memories and summary assembled for a run (ContextBundle)
Core Seleric Agent Core, the MCP gateway the agent reads data through

Domain health Per-domain snapshot of selected metrics with judgement of the latest value
Evidence A stored tool result row set (EvidenceArtifact) referenced by query_id
Grounding The deterministic check that each figure in an answer is measured or derived from tool results
Lane / lease A lease is the time-limited claim a worker holds on an attempt; renewed by heartbeat
Loop The single PydanticAI agent run that answers one turn
Memory A stored user, project, thread or episodic fact with consent state
Mission One execution of the loop (legacy name); a run has one mission
Outbox submission_outbox rows written with a submission so dispatch cannot be lost
Principal The authenticated caller: workspace, user, roles, method
Run The conversation-level record of one question's execution
Scratchpad Per-run ledger of facts already established, rendered back into the prompt
Target (monitoring) A floor, target and ceiling band for a metric
Trust gate Rules that set aside days whose data events make a metric unjudgeable
